テストは評価関数そのものなので、書いた本人の「これで十分」がいちばん当てにならない。
このスキルは、テストを書いた本人とは別の文脈（サブエージェント、または新しいセッション）で実行する。

## 手順
1. AGENTS.md・Issue・`scripts/check.sh`・テストを読み、仕様を箇条書きにする。
2. `$ARGUMENTS`（省略時は実装のディレクトリ）だけを書き換える誤実装を、12個以上考える。
   **生き残りそうなもの**を優先する。目安は次のとおり。
   - テストが見ていない項目の直書き・取り違え（一部の項目だけを assert していると通る）
   - 境界値（0、空、同じ日、うるう年、上限）
   - 敵対的なデータ（HTML・SQL を含む値、未知の列挙値、重複、順序）
   - 存在しない ID・不正な入力の扱い
   - 評価関数の外側（タイトル、エラー時の表示、ログに出る値など）
3. 誤実装を `.agent/mutants.json` に書き、`python3 scripts/mutate.py .agent/mutants.json` で流す。
   テスト・`scripts/`・フィクスチャは書き換えない。依存の準備が要るなら `MUTATE_SETUP` を使う。
4. 次の形で報告する。
   - 試した誤実装の表（内容 / 生き残った・検出された）
   - 生き残りごとに、違反した仕様、実際に起きる見込み（高・中・低）、それを落とすテストのコード
   - テスト自体の不安定さ（同じ誤実装で結果が揺れたら、`.agent/mutate-logs/` を添える）

## テストを直す側へ
- 生き残りを1つずつ assert で潰すより、**画面や出力のすべての項目を、手で書いた期待値の表と完全一致で比べる**テストを1本置くほうが、まとめて塞がる
- 期待値は、実装と同じ関数で組み立てない。実装の誤りをそのまま写してしまう
- 直したら、同じ `.agent/mutants.json` を流し直して、全部落ちることを確かめる
- 生き残りがあったことは、`/postmortem` で Evaluation として `docs/failures.md` に残す（テストを書いたのが人間でも同じ）

## いつ回すか
評価関数（テスト・check）を変えた PR では回す。実装だけを変えた PR では回さない（1回あたり check × 誤実装の数だけ時間がかかる）。
