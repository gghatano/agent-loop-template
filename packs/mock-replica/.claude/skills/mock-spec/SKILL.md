モックを、実装と評価関数の両方が参照できる仕様に落とす。**モックそのものは変更しない。**
出力はすべて下書きで、人間が確かめてから使う。特に「表示ルール」と「未定義」は人間が決める。

## 手順
1. `$ARGUMENTS`（省略時 `mock/`）の HTML と CSS をすべて読む。`docs/knowledge/mock-replica.md` と `docs/README.md` も読む。
2. `docs/spec/mock.md` に次を書く。冒頭の `sources` には、読んだモックのファイルをすべて並べる（モックが変わると spec が赤くなる）。規則には ID（`R-xx`）を付ける。
   - **画面一覧**：モックのファイル、実装のルート（決まっていなければ案）、モックが描いているデータの件数
   - **データ項目**：画面に出る値ごとに、項目名・型・モック上の値・どの画面のどこに出るか
   - **表示ルール**：生の値から表示への変換（金額・日付・期間・状態ラベル・件数など）。モック上の具体例を必ず添える。例が1つしかなく、ルールが一意に決まらないものは「未定義」に回す
   - **画面遷移**：モック間のリンク（どこを押すとどこへ行くか）。実装のルートでの対応も書く
   - **フォーム**：項目・型・必須・選択肢・ヒント文
   - 未定義のものは spec に書かない（次の手順で議論に出す）
3. モックからは決められないこと（例: 0件のとき、未知の状態、長い名前、同名、エラー時）を、`docs/discussions/<今日>-mock-undefined.md` に status: open で書く（`_template.md` の形）。項目ごとに、どの例があれば決まるかを添える。ここは人間に返す。
4. モック上のデータを `fixtures/` に書き出す。実装をこのデータで動かすと、モックと同じ画面になるようにする。
5. `vrt.json` を作る（`vrt.json.example` を参照）。画面ごとに、モックのファイルと実装のパスを対応させる。
6. `python3 scripts/docs_check.py --stamp docs/spec/mock.md` で出典のハッシュを記録する。
7. 画面ごとの Issue 案を `.github/ISSUE_TEMPLATE/mock-screen.yml` の形で出力する。作成は人間の確認を取ってから。

## 注意
- 表示ルールを推測で埋めない。例が足りないものは議論に出す
- 人間が未定義を決めたら、`docs/decisions.md` に記録し、`docs/design/` の該当の節に書く。spec はその節も `sources` に足して `/sync-spec` で追従する
- モックの CSS は読むが、実装用に書き換えたりコピーしたりしない
